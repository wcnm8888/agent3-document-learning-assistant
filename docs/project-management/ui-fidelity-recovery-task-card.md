## 1. 任务事实与目标

原 UI-HF0～UI-HF6 的功能性改造、定向测试和回归记录仍保留，但 2026-08-03 的真实浏览器复查表明：当前运行页面没有达到上述 Figma 的高保真视觉目标。因此，历史“`ready_for_release_review`”只表示当时的功能性/回归结论，不得再作为视觉验收通过的依据。

本任务要在**不改变既有业务语义**的前提下，让真实运行页面实现“知识工作台外壳 + 独立主工作区 + 上下文检查器”的结构、层级和响应式体验；验收以 Figma 对照和真实数据浏览器截图为准。

## 2. 范围与非目标

范围：应用外壳、空间导航、学习会话、消息时间线、Composer、文档库工具栏和文档行、文档详情检查器、来源/笔记、平板与移动端容器、视觉 QA。

非目标：PDF/Markdown 解析、分块、Embedding、Qdrant 检索、回答生成、SQLite Schema、会话/笔记/引用/生命周期业务规则、认证、多租户、Neo4j、公网部署。不得伪造文档、答案、来源、笔记或成功状态；不得处理 `upload_progress?upload_id=undefined` 404；不得删除真实文档或 Qdrant points。

## 4. P0 阻塞清单

1. 左侧导航说明文字侵入“学习报告”等导航项，发生可见重叠。
2. 会话状态/完整 `session_id` 使用原生可滚动区域，出现横向滚动条。

6. 当前实时实例中“文档库”导航点击后主工作区未切换，无法验收工具栏、紧凑文档行和详情检查器。

8. 多轮 `APP_CSS` 追加和多组媒体查询共同控制布局，存在级联冲突与重新引入重叠的风险。

## 5. 视觉契约（Visual Contract）

### 桌面结构

- 页面使用一个唯一工作台根容器；内容最大宽度 1160～1200px，居中，外侧留白随视口增长。
- 顶栏高度 56～64px：左侧品牌与副标题；右侧范围/本地运行状态/紧凑操作。不得出现独立的全宽原生页脚干扰工作台闭环。
- 工作台网格：左侧空间导航 168～192px、中间主工作区 `minmax(0, 1fr)`、右侧检查器 280～304px；间距 16～24px。中间工作区为视觉主角，三栏不得同权重。
- 左侧导航用独立“空间”分组、导航项、最近文档和底部环境说明组成纵向 Flex 流；说明文字不得绝对定位或覆盖导航项。
- 完整 `session_id`、`document_id`、hash 和原始 JSON 只放在可展开的二级详情中；首级界面仅显示可读短标识，长文本必须截断、复制或详情查看，不能产生横向滚动。

### 学习会话结构

- 标题区按“eyebrow → 标题/说明 → 范围与会话状态 → 新会话”组织；状态以短标签呈现，不能让原始 ID 参与网格排版。
- 时间线是主工作区的连续内容：用户问题气泡、助手回答卡、来源数量和“可保存为笔记”提示均绑定真实回调数据。
- 空时间线仅保留紧凑引导，最小高度以可视区域和 Composer 位置决定；不得因空值撑出大块空白。
- Composer 固定在会话工作区底部，视觉上与时间线连续；包含输入、提交、清空、键盘提示和加载/禁用反馈。底层仍调用现有问答回调。

### 文档库与详情结构

- 文档库标题区包含标题/说明、上传入口、搜索和筛选工具栏；工具栏与文档列表是一个主工作区，而非纵向表单堆叠。
- 文档项使用紧凑列表行：文件名与摘要、格式、文字状态标签、更新时间；长文件名两行截断，完整值在详情检查器可见。
- 右侧详情检查器始终对应当前选择文档，展示完整 `document_id`、hash、统计、错误详情与已有生命周期入口；按钮继续使用真实操作回调与确认语义。

### 来源、笔记与响应式

- 来源/笔记是检查器内的显式 Tab；PDF 卡必须显示页码，Markdown 卡必须显示章节、段落、行号。不可把两者降级成同一种“通用定位”。
- ≥1200px 采用三栏工作台；761～1199px 主工作区优先，导航与检查器可收缩为抽屉；≤760px 使用菜单进入导航、单主工作区和来源/笔记底部面板，文档详情为全屏抽屉或确认弹窗。
- 空、加载、成功、失败、禁用均要有明确文字与图标/样式，不能只依赖颜色；错误信息必须脱敏。

### 高保真与等效边界

必须高保真：工作台比例/层级、空间导航、会话标题/时间线/Composer、文档工具栏/文档行、检查器/Tab、移动容器。

允许等效：原生文件选择触发器、下拉框底层行为、原始 JSON 的二级展开、无障碍所需的原生控制；等效实现不得暴露为主要视觉结构。

## 6. 技术实施策略

1. 保留 `UIController`、现有服务层、RAG、SQLite/Qdrant 以及全部回调和状态对象。
2. 不再以“继续向单一 `APP_CSS` 末尾叠加覆盖规则”为修复方式。HF-R1 先建立唯一的外壳和断点归属，清理同一 UI 文件内相互竞争的布局职责；任何 CSS 修改必须替换/收敛冲突规则，而不是盲目追加。
3. 关键视觉区域可使用受控展示层（例如真实数据驱动的 `gr.HTML`/包装容器），但交互入口必须继续连接已有 Gradio 组件和回调；不得以静态 HTML 伪装真实数据。
4. 原生 `Chatbot`、`Dataframe`、`JSON`、`Accordion` 只能作为数据/无障碍/二级披露承载，或被视觉包装；最终主画面不得由其默认外壳决定。
5. 在临时 SQLite/Qdrant 与安全夹具中准备空知识库、真实文档列表、真实问答/来源/笔记和失败状态，供 HF-R5 截图对照；不触及真实生产数据。
